# 接口幂等性

网络超时后调用方分不清"请求到底成功没有"，只能重试。 **幂等**的意思是：同一个请求重复执行多次，
结果跟执行一次一样。这份文档说明哪些接口需要幂等、各自怎么做的、为什么这样做。对接方需要知道的
使用规则见 [api.md](api.md)"幂等"一节，这里讲设计和实现。

## 哪些接口需要幂等

判断标准： **重试一次会不会产生第二次副作用**。

| 类别                   | 接口                                                                          | 重试有副作用吗                                | 做法                     |
|------------------------|-------------------------------------------------------------------------------|-----------------------------------------------|--------------------------|
| 累加/创建类（相对量）  | `/account/balance`、`/account/credit`、`/order/add`、`/order/conditional/add` | 有：重复入账、额度翻倍、重复下单、重复冻结    | 幂等键 `requestId`       |
| 状态推进类             | `/account/round/close`                                                        | 有：把已经进入的下一轮又结束一次              | 幂等键 `round`（版本号） |
| 设为目标值类（绝对量） | `/position/leverage`、`/account/insured`、`/account/status`、`/index-price`   | 无：重复设置结果不变                          | 天然幂等，不需要         |
| 撤销类                 | 撤单、条件单撤销、`/order/cancel-all`                                         | 无副作用，重复调用返回 `order_not_cancelable` | 天然幂等，不需要         |
| 查询类                 | 所有 `GET`                                                                    | 无                                            | 天然幂等                 |

规律： **"加减一个量""创建一个东西""往前推进一个状态"要做幂等；"设置成某个值"和"撤销"天然幂等。**

## 统一的幂等键：`requestId`

订单、条件单、资金操作用同一个名字 `requestId`，规则完全一致：客户端生成（建议UUID）、字母数字和`_-`、
1~64位、同一个`uid`内唯一。订单原来叫 `clientOrderId`，后来统一成 `requestId`——资金操作没有"订单"的
概念，用中性的名字才能三处通用。

## 实现：三个部件

### 1. 数据库唯一索引占位

`orders`、`conditional_orders`、`member_transactions`各有一个 `(uid, request_id)` 唯一索引。没传
`requestId`的行是 `NULL`，MySQL 唯一索引允许多个 `NULL`，所以不带键的请求不受影响。

并发的重复请求靠这个唯一索引串行化：先到的事务持有索引项，后到的 `INSERT` 会 **阻塞**到先到的提交或回滚——
提交了就撞唯一索引、按重放处理；回滚了（比如余额不足）就自己接着往下执行。不需要额外的分布式锁。

### 2. 请求指纹，识别误用

只靠唯一索引，同一个 `requestId` 带了不同参数会被静默当成重复请求，返回第一笔的结果，调用方会误以为
第二笔也成功了。所以每次请求把关键参数按固定顺序拼起来取 SHA256（`service.RequestFingerprint`），
存在 `request_hash` 列里，重复提交时比对：一致就重放，不一致返回 `idempotency_conflict`。

指纹里要区分"没传"和"传了0"（`marginAmount` 没传跟传 `0` 语义不同），小数先规范化再拼（`1.50` 和 `1.5`
是同一个数）。拼接用 `0x1f` 分隔符，避免 `("ab","c")` 和 `("a","bc")` 拼出同一个串。

### 3. 涉及资金的操作放进同一个事务

`/account/balance` 和 `/account/credit` 要做两件事：写资金流水（占位幂等键）和改余额。这两步必须在同一个
数据库事务里（`AccountRepo.ApplyFundOp`），否则：

- **先写流水再改余额**：中间崩溃，流水记了钱却没动，之后重试被当成重复请求吞掉，钱永远补不上
- **先改余额再写流水**：中间崩溃，重试会再改一次余额，重复入账

放进一个事务：要么都生效要么都不生效。扣款余额不足时事务回滚，流水行一起撤掉， **这个 `requestId` 没有被
消耗**，补足余额后可以用同一个 `requestId` 重试。

**事务一开始先 `SELECT ... FOR UPDATE` 锁住账户行，让同一个账户的资金操作串行执行。** 这一步是review时
用真实并发压出来的：不加锁时，几个请求带同一个 `requestId` 并发、而先到的那个因余额不足回滚，后面几个会同时
拿到唯一索引冲突上的共享锁、再一起升级成排他锁，InnoDB 判定死锁并随机回滚几个——16 路并发实测约一半请求
返回 500。先锁账户行之后同样的压测（8 轮、每轮 24 路）零死锁、零 500。资金操作本来就低频，串行的代价可以忽略。
另外保留了一层兜底：撞上死锁（MySQL 错误 1213）自动整个事务重试，最多 3 次。项目其它地方有意不用事务（靠原子条件 UPDATE），但这两个
接口是单库单事务，是值得破例的地方。

## 结束本轮：用 `round` 当幂等键

`/account/round/close` 没有"幂等键"这个额外参数，因为要结束的 **那一轮的编号本身就是天然的幂等标识**——
这是业界常见的"版本号/状态条件更新"（CAS）思路：请求的含义是"把第 N 轮结束"，账户当前已经不在第 N 轮了
就什么都不做。

早期实现没有这个参数，引擎处理事件时读的是 **处理那一刻的当前轮**。合作方超时重试，第二个请求是全新的 Kafka
消息（消息级去重按 offset 判断，管不到"合作方又调了一次"），引擎会把已经进入的下一轮又结束一次：撤掉新一轮
刚挂的单、强平刚开的仓、清零刚发的信用额度。

现在有两层防护：

1. **API 层预检**：`round` 比账户当前轮数小 → 直接返回 `already_closed`；大 → `round_mismatch`；相等才发事件
2. **引擎层权威判断**：事件里带 `round`，处理时账户当前 `round` 不等于它就忽略。API 预检和引擎处理之间账户可能
   推进一轮（并发窗口），引擎这一层才是最终保证

部分失败（比如某个仓位缺标记价格没平掉）时 `round` 没有推进，用 **同一个 `round`** 重新调用就能重试——这也是
这个设计的一个好处：重试和防重复用的是同一个机制，不冲突。

## 已有的其它幂等保护（内部）

| 位置                             | 机制                                                                                                                 |
|----------------------------------|----------------------------------------------------------------------------------------------------------------------|
| Kafka 消费（下单/撤单/结束本轮） | `processed_messages` 表按 `(consumer_group, topic, partition, offset)` 去重，见 [message-dedup.md](message-dedup.md) |
| `EngineService.SubmitOrder`      | 委托状态检查 + `Book.Contains`，重复的下单事件不会二次撮合                                                           |
| 资金费率结算                     | `funding_rate_history` 的 `(symbol, funding_time)` 唯一索引                                                          |
| 结束本轮的最终结算               | `CloseRoundIfRound` 的 `WHERE round=?` 条件更新 + 分布式锁                                                           |
| 强平                             | `MarkLiquidating` 的 `WHERE status='normal'` 原子 guard                                                              |
| 下单落库后发 Kafka 失败          | 带同一个 `requestId` 重试会把委托补发，引擎侧对已处理的委托直接跳过                                                  |

## 业界常见方案，我们怎么选的

| 方案                         | 典型代表                                                                              | 我们的用法                                                               |
|------------------------------|---------------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| 天然幂等（设为目标值）       | REST 的 PUT 语义                                                                      | 改杠杆、设投保、喂指数价                                                 |
| 客户端幂等键 + 唯一索引      | Stripe `Idempotency-Key`、币安 `newClientOrderId`、OKX `clOrdId`、Bybit `orderLinkId` | 下单、条件单、充值、发额度（`requestId`）                                |
| 版本号 / 状态条件更新（CAS） | 乐观锁 `WHERE version=?`、状态机 `WHERE status=?`                                     | 结束本轮（`round`）、强平标记、订单/持仓更新                             |
| 业务天然唯一键               | 充值的链上 `txHash`                                                                   | 资金费率 `(symbol, funding_time)`                                        |
| 消费端去重表（inbox）        | 消息队列的 at-least-once + 幂等消费                                                   | Kafka `processed_messages`                                               |
| 服务端一次性 token           | 表单防重复提交                                                                        | 没用：多一次往返，交易类 API 很少用                                      |
| 分布式锁 / SETNX             | 防并发                                                                                | 只用来串行化并发下单的分档校验，**不**当幂等方案——它挡不住"过一会儿重试" |

跟 Stripe 的差异：Stripe 用请求头传键、键有 24 小时有效期；我们用 body 里的字段、键 **永久有效**（跟订单/流水
同生命周期，不做过期清理）。永久有效更简单也更安全（不会出现"键过期后同一个请求被当成新请求"），代价是唯一索引
会随数据增长，量级跟订单表、流水表本身一致，不额外增加负担。

## 已知边界

- **`requestId` 只在同一类资源、同一个 `uid` 内唯一**：订单、条件单、资金流水各自独立。资金类的两个接口共用一个空间，
  所以同一个 `requestId` 先充值再发额度会被判冲突。用 UUID 就没有这个问题
- **条件单触发后落地的委托不继承 `requestId`**：如果继承，条件单和一笔普通委托恰好用了同一个键时，触发落库会撞
  `orders` 表的唯一索引，走"落库失败补偿"路径把这次触发白白取消
- **撤单重复调用返回错误而不是成功**：`order_not_cancelable` 是安全的（没有副作用），调用方按"已经撤了"处理即可。
  Stripe 风格是重放原响应，这里选择保持错误码，让调用方能区分"这次真的撤了"和"早就撤过了"
- **重放返回的是当前状态的简化结果**，不是第一次响应的逐字节拷贝：订单重放返回 `orderId`，不会重放当时的其它信息
  （后续状态用 `GET /order/detail` 查）
