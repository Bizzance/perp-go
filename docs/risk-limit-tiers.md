# 保证金分档（风险限额）

维持保证金率和最大杠杆不是每个合约一个固定值，而是按 **仓位名义价值**分档：名义价值越大，
风险越高，维持保证金率越高，允许的最大杠杆越低——防止巨鲸仓位跟小仓位用同样的杠杆倍数。

## 数据结构

`risk_limit_tiers`表，一个symbol配多档：

| 字段                      | 含义                                                      |
|---------------------------|-----------------------------------------------------------|
| `tier`                    | 档位序号，从1开始，越大风险越高                           |
| `max_notional`            | 本档名义价值上限，**0代表这一档不限（约定放在最后一档）** |
| `maintenance_margin_rate` | 本档维持保证金率                                          |
| `maintenance_amount`      | 速算扣除数，见下面公式                                    |
| `max_leverage`            | 本档最大杠杆                                              |

维持保证金公式：

```
维持保证金 = 名义价值 × maintenance_margin_rate − maintenance_amount
```

`maintenance_amount`是配置时手工算好的常量（不是运行时推导），保证跨档位边界时数值连续，
不会出现跳变——每一档的值 = 上一档在其上限名义价值处的维持保证金，减去本档费率在同一个
名义价值下算出来的数值。`sql/schema.sql`里的种子数据已经按这个公式算好，改配置时要保持
这个连续性。

## 查找逻辑（`PositionService.TierFor`）

按`tier`升序找第一个`max_notional`覆盖到目标名义价值的档位。这里有两个安全校验， **任何
一个不满足都按"没有配置分档"处理**（调用方有现成的安全兜底：开仓直接拒绝，维持保证金
计算跳过这个仓位并打日志）：

1. **单调性**：`tier`序号升序必须等于`max_notional`升序。如果配置时把两档的`max_notional`
   填反了，会导致静默命中错误的档位——风控失效但没有任何报错，比"没配置"更隐蔽。
2. **末档必须是0（不限）**：如果名义价值超过了最后一档的`max_notional`，且最后一档不是0，
   说明配置漏配了"不限"档，不是名义价值真的超出了业务上限——不能悄悄套用最后一档的参数
   蒙混过关。

这两条校验失败都会打`[ERROR]`日志，配置分档时要留意日志。

## 开仓杠杆校验

杠杆上限按"这笔单子成交后，这个方向仓位的名义价值"落在哪一档来判断， **不是**看这笔单子
自己的名义价值。这么做是为了防止拿现有仓位垫底、每次都用小单子叠加最高杠杆来绕开分档
限制。具体算法（`router.go`的`addOrder`）：

```
projectedNotional = 已成交仓位名义价值 + 同方向还在排队的OPEN挂单名义价值 + 这笔新委托的名义价值
tier = TierFor(symbol, projectedNotional)
要求 leverage <= tier.MaxLeverage
```

三部分的估值口径不一样，都是为了防止用户用虚报价格操纵计算结果：

- **已成交仓位**：用当前标记价格估值（mark-to-market），标记价格缺失才退回持仓均价
- **排队中的挂单**：用挂单自己的委托价格（`o.Price`）——这是已经过校验、真实挂在簿子上的
  委托，价格是真实的，不能像"新委托"那样怀疑
- **这笔新委托自己**： **只在SHORT+OPEN方向**用`max(委托价, 标记价)`取更保守的值——
  SHORT+OPEN在撮合引擎里是卖方向，报价远低于市价属于"吃单价"，会立刻按盘口对手的真实
  价格成交，不是按填的这个低价；LONG+OPEN反过来，报价远低于市价是完全合法的被动挂单
  （买跌），只会按这个低价成交，不需要也不应该套用标记价格，否则会把正常订单误判进
  更严格的档位、平白无故拒单

## 平仓单不校验分档

平仓单只过一道跟分档配置无关的`maxSaneLeverage`（1000）离谱值兜底，不查`risk_limit_tiers`。
两个原因：

1. `leverage`字段只有开仓时用来算冻结多少保证金，平仓不创建新仓位/新风险
2. 分档校验依赖`risk_limit_tiers`有配置——如果平仓也要求配置存在，一旦运营误删了分档
   配置，会把用户已有仓位卡死平不掉，这比"平仓单杠杆字段没有精确校验"严重得多

## 强平判断和展示也用同一套分档

- **维持保证金总额**（`PositionService.MaintenanceMarginTotal`，强平判断用）：对uid名下
  每个仓位分别查它当前名义价值对应的档位，加总。 **任何一个仓位缺标记价格或缺分档配置，
  只跳过它自己这一份贡献（记0并打警告日志），不能因为一个symbol缺数据就让整个uid的
  风控扫描都跳过**——那样会连累这个用户名下其它数据齐全、可能已经在爆仓边缘的仓位也
  一起被放过。
- **预估强平价展示**（`Position.LiquidationPrice`）：同样用当前名义价值对应的档位算，
  仅供展示参考，真实强平判断以维持保证金总额为准。

已知的残留风险：如果一个仓位的分档配置是在仓位已经开仓之后才被删掉/改坏的，它的维持
保证金贡献会变成0，但它的未实现盈亏依然会正常计入账户权益——也就是说这个仓位可以持续
亏损而不会成为触发强平的原因（虽然亏损本身仍然会拖累账户权益，最终可能因为其它仓位的
维持保证金要求间接触发强平）。这是一个操作失误（配置被移除）触发的边缘场景，MVP阶段
选择打日志告警而不是引入更复杂的兜底机制。
