# 鉴权方案（设计稿，尚未实现）

**这份文档是待实现的方案，不是当前代码的行为。** 当前 `contract-api` 没有任何鉴权，所有接口靠请求里
明文的 `uid` 识别账户，见 [api.md](api.md)"鉴权"一节。正式让合作方对接之前必须落地，否则任何能访问端口
的人都能给任意账户加钱、喂指数价、下单、撤单。

## 要保护什么，威胁模型

合作方（客户端）是**服务端**，用户不会直接调本系统。所以要解决的是"这个请求是不是真的来自合作方"，
不是"这个终端用户是谁"——终端用户的身份验证是合作方自己系统的事，本系统信任合作方传过来的 `uid`。

| 风险                                                              | 现状                       |
|-------------------------------------------------------------------|----------------------------|
| 第三方冒充合作方调用接口（加钱、下单、撤单、结束本轮）            | 完全没防                   |
| 请求被中间人截获后**重放**（比如重放一次加钱）                    | 完全没防                   |
| 请求在传输中被篡改（金额、uid）                                   | 靠 HTTPS，应用层没防       |
| 合作方的普通交易凭证被用来调运营接口（`/account/balance`、`/index-price`） | 没有权限分级       |
| WS 私有频道 `user:{uid}` 谁都能订阅任意 uid                       | 没防                       |

## 推荐方案：API Key + HMAC-SHA256 请求签名

### 凭证

每个合作方分配一对：`apiKey`（公开标识，随请求发送）和 `secret`（只有双方知道，**永远不随请求发送**）。
`secret` 服务端存哈希不可逆的话验不了签名，所以要存可还原的形式——放配置/密钥管理服务，不要落业务库明文，
不要出现在日志里。

### 请求头

| Header            | 内容                                                              |
|-------------------|-------------------------------------------------------------------|
| `X-Api-Key`       | 合作方的 `apiKey`                                                 |
| `X-Timestamp`     | 毫秒时间戳                                                        |
| `X-Nonce`         | 随机串（16~32位），每个请求唯一                                   |
| `X-Signature`     | 十六进制小写的 `HMAC-SHA256(secret, 待签名串)`                    |

### 待签名串

```
待签名串 = timestamp + "\n" + nonce + "\n" + method + "\n" + path + "\n" + 排序后的query + "\n" + sha256hex(body)
```

- `method` 大写（`POST`），`path` 不含 query（`/order/add`）
- query 按参数名字典序排序后再拼成 `a=1&b=2`；没有 query 就是空串
- body 是**原始字节**的 SHA256（GET 请求 body 为空，就是空串的 SHA256），不要重新序列化 JSON 再算——不同语言序列化出来的字节不一样，签名会对不上

### 服务端校验

1. `X-Api-Key` 存在且启用，取出对应 `secret`
2. **时间窗**：`|now - timestamp| <= 30s`，防止截获后过一会儿再重放
3. **防重放**：`nonce` 在 Redis 里 `SETNX apiKey:nonce EX 60`，已存在就拒绝——时间窗内的同一个请求也不能重放第二次（`requestId` 只是业务幂等，挡不住"重放一次加钱"）
4. 重新计算签名，**用常量时间比较**（`hmac.Equal`），不匹配就拒绝
5. 全部通过才放行，并把 `apiKey` 对应的合作方身份放进请求上下文

失败统一返回 `code=401`：`errCode` 分 `auth_missing`（缺头）、`auth_expired`（时间窗外）、`auth_replayed`（nonce 重复）、
`auth_invalid_signature`（签名不对）。**不要区分"key 不存在"和"签名错"**，避免被拿来枚举有效 key。

### 落到代码里

在 Gin 里加一个中间件，挂在 `Router()` 上，`uid` 保持独立参数不动（[api.md](api.md)里已经承诺过后续换鉴权中间件不改接口入参）：

- 新增 `internal/api/auth.go`：`AuthMiddleware(keys KeyStore, cache *cache.Cache)`
- 读 body 校验签名后要把 body 放回去（`c.Request.Body = io.NopCloser(bytes.NewReader(raw))`），否则后面的 `ShouldBindJSON` 读不到
- `/health` 免鉴权（探针用）；`/ws` 见下面

## 权限分级：运营接口和交易接口分开授权

现在所有接口一视同仁，但合作方的**业务后端**需要的和**运营/行情源**需要的权限差别很大：

| 级别      | 接口                                                                                                  |
|-----------|-------------------------------------------------------------------------------------------------------|
| `trade`   | 下单、撤单、批量撤单、条件单、改杠杆、全部查询类接口、结束本轮                                        |
| `ops`     | `POST /account/balance`（加钱扣钱）、`POST /account/credit`（发额度）、`POST /account/insured`、`POST /index-price` |

每个 `apiKey` 带一个 scope 集合，中间件按路由检查。**`/index-price` 尤其要单独授权**：它直接决定标记价格和资金费率，
喂一个假价格就能触发批量强平。

## WebSocket 鉴权

私有频道 `user:{uid}` 现在谁都能订阅任意 uid。方案：

- 连接 `/ws` 时带上同样的三个头（`X-Api-Key`/`X-Timestamp`/`X-Nonce`/`X-Signature`，`method=GET`、`path=/ws`），握手时校验，通过后这个连接绑定合作方身份
- 订阅 `user:{uid}` 时检查这个 `uid` 是否属于该合作方（见下面"uid 归属"）
- 公开频道（`depth`/`trade`/`kline`/`markprice`）不需要额外校验，但连接本身仍然要通过握手鉴权，避免匿名连接耗资源

## uid 归属（多合作方时才需要）

只有一个合作方时，`uid` 都归它，不用管。如果以后有多个合作方，需要防止合作方 A 用自己合法的凭证操作合作方 B 的 `uid`：

- 方案一：`uid` 按合作方分段（比如每个合作方一段号码），中间件按 `apiKey` 校验 `uid` 落在自己的段内。简单、无状态
- 方案二：`accounts` 表加 `partner_id` 列，在 `POST /account/create` 创建账户时绑定，之后校验。灵活但要改表、每个请求多一次查询（创建接口就是天然的绑定点）

单合作方阶段建议先不做，等真的有第二个合作方再定。

## 其它配套

- **限流**：按 `apiKey` 限流（Redis 计数，滑动窗口），超限返回 `code=429`、`errCode=rate_limited`。下单类和查询类分开配额
- **IP 白名单**：合作方是固定出口的服务端，可以在 `apiKey` 上再绑一组来源 IP，作为签名之外的第二道防线
- **HTTPS**：签名不加密内容，传输保密靠 TLS，必须在网关/负载均衡层终止 TLS
- **密钥轮换**：每个合作方允许同时存在两把有效 `secret`，切换期新旧都能验，合作方切完后作废旧的
- **审计**：每个通过鉴权的请求记 `apiKey`+路径+`uid`+结果，出问题能追到是哪个合作方哪个凭证

## 实现前需要跟合作方确认的事

1. 合作方已有的鉴权习惯：如果他们对接别的交易所用过 HMAC 签名（币安、OKX 这类），可以直接对齐同样的头名和待签名串格式，他们接入成本最低
2. 他们的服务是不是固定出口 IP（决定 IP 白名单能不能用）
3. 是一个合作方还是以后会有多个（决定要不要做 `uid` 归属）
4. 运营接口（加钱、喂指数价）是合作方的业务后端调，还是我们自己的运营系统调（决定 `ops` scope 发给谁）
