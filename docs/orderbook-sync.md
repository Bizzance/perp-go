# 订单簿镜像与行情同步

把币安的订单簿镜像成系统账户的真实挂单、把币安的指数价和K线同步进我们系统。**用户下单，对手方就是系统**：
没有做市商，也不对冲。撮合、结算、保证金、强平、资金费率、持仓这些逻辑完全不变，跟真实U本位合约一样，
变的只是"币安订单簿怎么进撮合引擎"这一层机制。生产环境必须部署。把币安的行情数据（盘口、K线）转发给
合作方的合规性已经确认。

**这是两个不同职责、分别放在不同进程里的东西**：

- **订单簿镜像**：要直接碰撮合引擎的内存订单簿和账户的保证金/持仓，做在`contract-engine`进程内部
  （`internal/service`的`MirrorService`），进程内直接调用Go函数，不经HTTP、不经Kafka、不需要分布式锁
- **指数价、K线同步**：是`contract-api`要对外提供的行情数据，不碰撮合引擎内部状态，继续用独立进程
  `orderbook-sync`（代码在`internal/booksync/`），通过公开的运营接口推送

## 订单簿镜像（contract-engine内部）

每一轮（默认1秒），对每个自己负责的合约（分片部署下只镜像`PERP_ENGINE_SYMBOLS`里的symbol）：

1. 拉币安USDⓈ-M合约深度的前N档（默认50档），价格和数量**原样**，数量只按我们合约的`base_coin_scale`和`volume_step`向下取整、低于最小下单量的不挂
2. 用一个系统账户（`service.UID`，固定值不需要配置）在撮合引擎的内存订单簿里直接挂出一模一样的单子：买盘方向`long`、卖盘方向`short`，
   同一个账户可以同时持有两个方向的仓位（`positions`表按`uid+symbol+side`存，不需要像早期版本那样拆两个账户）。
   用户的市价单、能立即成交的限价单吃的就是这些挂单，对手方是这个系统账户
3. 系统账户由`contract-engine`启动时自己建好并充值（配置的余额，默认10亿USDT，低于一半自动补），不经过
   `POST /account/create`这类对外接口，不用手动创建或管理

跟已经挂着的单子做差异，**只在价位变了或者被用户吃掉大半时才动**，不会为了币安数量的小幅波动天天撤了重挂（那样订单簿里的排队位置会一直丢）。

早期版本（独立的`orderbook-sync`进程，通过公开下单/撤单API+分布式锁挂单）出过历史挂单堆积、把数据库拖垮的故障
（挂单数堆到几千笔，MySQL被拖到高负载，越挂不上越堆积），因为镜像挂单被当成"跟合作方一样的外部请求"套用了
为多进程并发设计的分布式锁和异步撤单确认，而镜像挂单其实从来只有一个来源。现在挂单/撤单是进程内同步调用
（函数返回就是生效的），这类问题不再存在。

### 不会出现买盘或卖盘为空，也不会交叉

行情单边移动时，整个一侧的档位都要换。这里有两个要求：

- 系统账户自己的买卖挂单不能真的撮合成交（会把最新成交价拖回过期的价格）——这个由`matching.Book`本来就有的
  自成交保护（STP）兜底：新挂单如果跟本账户还没撤掉的旧挂单撞上了，STP会自动摘掉那笔旧挂单（不产生成交），
  不需要额外处理
- 任何时候不能有一侧是空的，否则用户的市价单一笔都吃不到——做法是每一轮**先把新档位全部挂上，再撤掉过期的旧档位**，
  新旧短暂重叠的窗口里两侧都不空；因为挂单/撤单都是同步生效，这个窗口只有一次函数调用的时间，不像早期版本
  那样需要轮询等待撤单生效（最多1秒）

实测（真实的币安、整套系统）：连续采样100次，买盘、卖盘为空的次数都是0。

## 大单：让它吃

用户的大单一次吃掉很多深度，**就让他吃**：成交均价、开仓价、强平价都按真实成交算，币安的深度下一轮就补回来。不做任何特殊处理。实测：

| 市价买  | 结果                                                                                 |
|---------|--------------------------------------------------------------------------------------|
| 0.5 BTC | 全部成交，成交价=币安当时的卖一                                                      |
| 5 BTC   | 全部成交，均价比卖一高约4.8美元（真实吃深度的滑点）                                  |
| 50 BTC  | 成交20.544 BTC（我们同步的50档的总深度），均价比卖一高约3.1美元，其余自动撤销；成交后深度补回 |

要注意的几点：

- **能吃多少取决于镜像了多少档**（`PERP_MIRROR_LEVELS`，默认50，币安接口上限1000）。吃不满的部分自动撤销，价格不会被推到没有深度的地方。想让用户能成交更大的量，就调大它，代价是订单簿里的挂单更多
- 想限制单笔大小或价格范围，用现有的合约配置，不需要新代码：`coins.max_volume`（单笔最大量，0=不限）、`coins.price_protection_ratio`（市价单最多吃到参考价上下多少，种子数据是5%）
- 一个超大单吃光了全部镜像的档位时，那一侧会空到下一轮补回（最多一个间隔）。这是深度被真实吃光，不是镜像的问题；镜像更多档位、缩短间隔可以缩小这个窗口

## K线：全部用币安的（orderbook-sync进程）

`PERP_KLINE_SOURCE=external`（contract-api 和 contract-engine 都要设，生产模板已经设了）时，K线**只来自币安**，我们自己的成交不写K线，
不画。合作方拿到的K线（REST `GET /kline` 和 WebSocket `kline` 频道）就是币安的K线，24h涨跌、最高最低、成交量也是，最新价用最近一根1分钟K线的收盘价。
详见 [kline.md](kline.md)。

- 六个周期（1m/5m/15m/1h/4h/1d）各自从币安拉。**启动时补500根历史**（`BOOKSYNC_KLINE_BACKFILL`，币安接口上限1500），之后每2秒（`BOOKSYNC_KLINE_INTERVAL_SEC`）
  同步一次最近几根，只推变了的
- 中间断了一阵（币安或我们的api不可用），恢复后按错过的根数自动补上，不用重启
- 一次请求的体积有64KB上限，所以历史分批推（每批200根）
- 每个周期独立：一个周期拉不到不影响别的
- **成交量和成交笔数是币安全市场的**，不是我们平台的，对接时要跟合作方说明
- K线同步没配好（contract-api 没设 `external`）时日志里是 `[WARN] 同步币安K线失败 ... 需要设置PERP_KLINE_SOURCE=external`，K线是空的

## 币安拉不到怎么办

**订单簿镜像**（contract-engine）：

- **10秒以内**（`PERP_MIRROR_STALE_SEC`）：不动已经挂着的镜像单，可能只是一次抖动
- **超过10秒**：撤掉这个合约的全部镜像挂单，此时订单簿两侧都是空的。**这是有意的取舍**：过期的报价留在订单簿里，谁比我们更早看到币安的价格，
  谁就能按旧价成交。想更倾向于"一直有报价"可以把这个时间调大，风险自己权衡
- 币安恢复后自动重新镜像。**进程退出不会主动撤掉挂单**（不像早期独立进程版本那样有专门的退出清理）——`contract-engine`本来就随时可能重启，
  重启后从数据库恢复订单簿（含镜像挂单），下一轮判断这批挂单是不是还符合当前币安价位，该撤的照常撤
- 币安的行情接口在部分地区会返回451，部署前要确认能稳定访问

**指数价、K线**（orderbook-sync进程）：推送失败只记日志重试，contract-api在指数价30秒没更新后冻结标记价、暂停强平，见 [mark-price.md](mark-price.md)。

## 配置

### 订单簿镜像（`PERP_MIRROR_*`，contract-engine读取）

环境变量，不合法进程直接退出：

| 变量                     | 默认                   | 含义                                                                  |
|--------------------------|------------------------|-----------------------------------------------------------------------|
| `PERP_MIRROR_SYMBOLS`    | 空（不开启）           | 要镜像的合约，必须是币安上也有的合约名——留空表示不开启镜像，生产环境必须显式设置 |
| `PERP_MIRROR_LEVELS`     | 50                     | 每侧镜像币安盘口的前多少档，上限1000                                  |
| `PERP_MIRROR_INTERVAL_MS`| 1000                   | 每一轮的间隔                                                          |
| `PERP_MIRROR_LEVERAGE`   | 5                      | 镜像挂单的杠杆。全部保证金分档里最低的最大杠杆是5，用5在哪个档位都不会被拒 |
| `PERP_MIRROR_BALANCE`    | 1000000000             | 系统账户的余额（USDT），低于一半时自动补到这个数                      |
| `PERP_MIRROR_STALE_SEC`  | 10                     | 币安数据超过这么久没拉成功，就撤光镜像挂单                            |
| `PERP_MIRROR_BINANCE_URL`| `https://fapi.binance.com` | 币安合约行情地址                                                  |

### 指数价、K线同步（`BOOKSYNC_*`，orderbook-sync进程读取）

| 变量                     | 默认                   | 含义                                                                  |
|--------------------------|------------------------|-----------------------------------------------------------------------|
| `BOOKSYNC_API_URL`       | `http://127.0.0.1:7001` | contract-api地址（compose里是`http://api:7001`）                      |
| `BOOKSYNC_API_KEY_ID`    | 必填                   | API Key的id，**只需要`ops`权限**（指数价、K线同步都是运营接口）        |
| `BOOKSYNC_API_SECRET`    | 必填                   | 对应的secret                                                          |
| `BOOKSYNC_SYMBOLS`       | `BTCUSDT,ETHUSDT`      | 要同步的合约                                                          |
| `BOOKSYNC_INTERVAL_MS`   | 1000                   | 指数价每一轮的间隔                                                    |
| `BOOKSYNC_KLINE_INTERVAL_SEC` | 2                  | K线每隔多少秒同步一次最近几根；设0=不同步K线（contract-api没设`external`时用，否则每次都被拒绝） |
| `BOOKSYNC_KLINE_BACKFILL` | 500                    | 启动时（和断了很久之后）每个周期最多补多少根历史，上限1500            |
| `BOOKSYNC_BINANCE_URL`   | `https://fapi.binance.com` | 币安合约行情地址                                                  |

## 部署

订单簿镜像在`contract-engine`进程内部，跟着这个进程一起部署，**生产必须在`deploy/.env`里配置`PERP_MIRROR_SYMBOLS`**（`deploy/.env.prod.example`
已经给了示例值），不需要额外的镜像/容器/密钥。

指数价、K线同步是独立进程，镜像有独立的`booksync`target，compose里的`booksync`服务在`booksync`这个profile下：
**生产环境在`deploy/.env`里设`COMPOSE_PROFILES=booksync`**（`deploy/.env.prod.example`已经设了）。先在`PERP_API_KEYS`
里加一把 `booksync:<secret>:ops`，再把同一个id和secret填到`BOOKSYNC_API_KEY_ID`、`BOOKSYNC_API_SECRET`。进程不监听端口，
靠日志和`restart: unless-stopped`。

测试环境默认不开镜像：模拟客户端的做市（[sim-client.md](sim-client.md)）也会往订单簿里挂币安的盘口，**两者用同一段系统账户uid，不能同时跑**。

## 日志

订单簿镜像（contract-engine）：

| 日志                                                          | 含义                                                       |
|---------------------------------------------------------------|------------------------------------------------------------|
| `[WARN] 订单簿镜像失败, symbol=...`                           | 这一轮失败（币安或数据库出错），每个合约每30秒最多一条     |
| `[ERROR] 币安数据已经超过10s没更新，已撤掉全部镜像挂单、暂停报价` | 币安拉不到超过阈值。**要马上查**，此时这个合约的订单簿是空的 |
| `[INFO] 币安数据恢复，重新镜像订单簿`                         | 恢复了                                                     |
| `[WARN] 订单簿镜像没有开启(PERP_MIRROR_SYMBOLS没配)`           | 启动时没配置，订单簿会一直是空的（除非有真实用户互相挂单成交） |

指数价、K线同步（orderbook-sync）：

| 日志                                                          | 含义                                                       |
|---------------------------------------------------------------|------------------------------------------------------------|
| `[WARN] 同步币安指数价失败`                                   | 指数价没推成功。服务端跳变保护拦下时也是这条                |
| `[WARN] 同步币安K线失败`                                      | K线没推成功                                                 |

## 已知限制

- **不对冲，没有敞口限额**：系统是用户唯一的对手方，用户整体盈利时系统亏损，没有上限保护。系统账户的余额是配置的虚拟资金（默认10亿USDT），没有真实的资本约束
- **盘口比币安有延迟**：REST轮询每秒一次，行情快的时候我们的最优价会落后币安。实测（一个波动很大的时段，2秒内币安价格变动近40美元）：
  我们的买一卖一相对币安平均落后约2.5美元（0.003%），最大约21美元（0.026%）。**谁比我们更早看到币安的价格，谁就有套利空间**，
  降低这个风险靠缩短间隔（`PERP_MIRROR_INTERVAL_MS`）、以后改用WebSocket
- **用户的限价单可能改变我们的盘口**：订单簿引擎没变，用户挂在买卖价差里的限价单会成为新的买一/卖一，用户之间也可能互相成交。此时我们的盘口就不再完全等于币安
- **系统账户的仓位会累积**：多空各一份、不轧差，用余额兜着。用户结束本轮、被强平时的强制结算按标记价进行，没有对手方记账，系统的敞口在账上看不见
- **K线、24h统计的成交量是币安全市场的**，不是我们平台的；24h统计是最近24根1小时K线聚合，跟币安的滚动24h行情有约1%的差异
- **只有币安一家来源**：盘口、指数价和K线都来自币安，没有多来源交叉校验。指数价有服务端的跳变保护兜底（`PERP_INDEX_MAX_JUMP`，见 [mark-price.md](mark-price.md)）
- **数量精度跟着我们的合约配置走**：种子数据里ETHUSDT的`base_coin_scale`是2位、`volume_step`是0.01，币安更细的数量会被截掉，要跟币安一致需要调大这两个配置（`coins`表，见 [api.md](api.md)）
- **分片部署下每个engine实例独立镜像自己负责的symbol**：不会重复镜像，但每个实例各自维护一份系统账户余额的读写，高频分片切换（几乎不会发生）理论上可能有短暂的账户状态竞争，跟其它涉及账户的并发场景是同一类简化

## 测试

`internal/binancefeed/`：币安客户端和"目标深度跟已有挂单做差异"的纯函数，币安用假的httptest服务：

- **纯逻辑**：前N档原样、数量按合约精度取整、低于最小量不挂、差异计划（保留/撤/重挂/重复）、补挂的顺序规则
- **币安拉取**：响应解析、各种异常（451/429、空盘口、交叉、格式错误、价格为0）、指数价解析、K线解析

`internal/service/mirror_integration_test.go`（真实MySQL+Redis+撮合引擎）：镜像挂单跟币安深度一致、盘口没变不重复挂撤、
**真实用户的市价单能吃到镜像挂单并正常结算（撮合/持仓/保证金走的是跟真实用户完全一样的路径）**、币安拿不到时按阈值撤光/恢复后重挂。

`internal/booksync/`（现在只剩指数价、K线推送）：币安用假的httptest服务，contract-api用假的内存后端：指数价每轮推送、失败重试、
多合约互相独立；K线六个周期各补历史、之后只同步最近几根、断了一阵后按错过的根数补、历史分批（200根一批）、api拒绝时不算已同步、
一个周期失败不影响别的、每个合约各自同步、可以关闭。API侧（集成测试）：整根覆盖不是合并、只推变了的、非external时拒绝、
整批校验（每种不合法的情况）、一批最大根数、最新价用币安K线收盘价、24h统计来自币安1小时K线。

另外用**真实的币安和整套系统**（api、engine、MySQL、Redis、Kafka）联调过：盘口价格与币安一致、指数价自动推进来、真实用户的市价单吃到系统的挂单、
大单的成交量和均价、进程重启后镜像恢复正常。这一步依赖外网，没有做成自动化测试。
