# 订单簿同步（orderbook-sync）

把币安的订单簿、指数价和K线同步进我们系统。**用户下单，对手方就是系统**：没有做市商，也不对冲。代码在`internal/booksync/`（逻辑）和
`cmd/orderbook-sync/`（进程入口），生产环境必须部署。

## 怎么工作

每一轮（默认1秒），对每个合约：

1. 拉币安USDⓈ-M合约深度的前N档（默认50档），价格和数量**原样**，数量只按我们合约的`base_coin_scale`向下取整、低于最小下单量的不挂
2. 用两个系统账户在我们的订单簿里挂出一模一样的单子：买盘账户（uid = `BOOKSYNC_UID_BASE`，开多挂买单）、卖盘账户（uid + 1，开空挂卖单）。
   用户的市价单、能立即成交的限价单吃的就是这些挂单，对手方是系统账户
3. 把币安的指数价推给contract-api（`POST /index-price`），标记价靠它做锚。没有它生产环境没有标记价，市价单和强平都不能用
4. 把币安的K线推给contract-api（`POST /kline/sync`），K线、24h统计、最新价都用币安的，见下面"K线"

跟已经挂着的单子做差异，**只在价位变了或者被用户吃掉大半时才动**，不会为了币安数量的小幅波动天天撤了重挂（那样每秒几十个请求，还会丢排队位置）。

## 不会出现买盘或卖盘为空，也不会交叉

行情单边移动时，整个一侧的档位都要换。这里有两个要求互相冲突：

- 两个系统账户的挂单不能交叉，否则会在两个系统账户之间真实成交，把最新成交价拖回过期的价格。撤单是异步的（经Kafka），
  撤单请求返回不代表引擎已经摘掉了旧单，新买单又不能高于还没摘掉的旧卖单
- 任何时候不能有一侧是空的，否则用户的市价单一笔都吃不到

做法是**先挂新单、再撤旧单**（以上涨为例）：旧卖单价格偏低，是过期的报价，立刻撤，同时挂出更高价的新卖单，卖盘不空；
新买单要等旧卖单撤掉才能挂，所以**旧买单先留着**（只是价格偏低，没有害处），轮询等旧卖单真的撤掉，同一轮里挂上新买单，最后才撤旧买单，
买盘也不空。等不到撤单生效（最多1秒）就留到下一轮，宁可这一轮少几档，也不冒交叉的风险。下跌时对称。

实测（真实的币安、整套系统）：连续采样100次，买盘、卖盘为空的次数都是0（改之前是10%和5%）。

## 大单：让它吃

用户的大单一次吃掉很多深度，**就让他吃**：成交均价、开仓价、强平价都按真实成交算，币安的深度下一轮就补回来。不做任何特殊处理。实测：

| 市价买  | 结果                                                                                 |
|---------|--------------------------------------------------------------------------------------|
| 0.5 BTC | 全部成交，成交价=币安当时的卖一                                                      |
| 5 BTC   | 全部成交，均价比卖一高约4.8美元（真实吃深度的滑点）                                  |
| 50 BTC  | 成交20.544 BTC（我们同步的50档的总深度），均价比卖一高约3.1美元，其余自动撤销；成交后深度补回 |

要注意的几点：

- **能吃多少取决于同步了多少档**（`BOOKSYNC_LEVELS`，默认50，币安接口上限1000）。吃不满的部分自动撤销，价格不会被推到没有深度的地方。想让用户能成交更大的量，就调大它，代价是订单簿里的挂单更多
- 想限制单笔大小或价格范围，用现有的合约配置，不需要新代码：`coins.max_volume`（单笔最大量，0=不限）、`coins.price_protection_ratio`（市价单最多吃到参考价上下多少，种子数据是5%）
- 一个超大单吃光了全部同步的档位时，那一侧会空到下一轮补回（最多一个间隔）。这是深度被真实吃光，不是同步的问题；同步更多档位、缩短间隔可以缩小这个窗口

## K线：全部用币安的

`PERP_KLINE_SOURCE=external`（contract-api 和 contract-engine 都要设，生产模板已经设了）时，K线**只来自币安**，我们自己的成交不写K线，
不画。合作方拿到的K线（REST `GET /kline` 和 WebSocket `kline` 频道）就是币安的K线，24h涨跌、最高最低、成交量也是，最新价用最近一根1分钟K线的收盘价。
详见 [kline.md](kline.md)。

- 六个周期（1m/5m/15m/1h/4h/1d）各自从币安拉。**启动时补500根历史**（`BOOKSYNC_KLINE_BACKFILL`，币安接口上限1500），之后每2秒（`BOOKSYNC_KLINE_INTERVAL_SEC`）
  同步一次最近几根，只推变了的
- 中间断了一阵（币安或我们的api不可用），恢复后按错过的根数自动补上，不用重启
- 一次请求的体积有64KB上限，所以历史分批推（每批200根）
- 每个周期独立：一个周期拉不到不影响别的
- **成交量和成交笔数是币安全市场的**，不是我们平台的，对接时要跟合作方说明
- K线同步没配好（contract-api 没设 `external`）时日志里是 `[WARN] 同步币安K线失败 ... 需要设置PERP_KLINE_SOURCE=external`，K线是空的

## 币安拉不到怎么办

- **10秒以内**（`BOOKSYNC_STALE_SEC`）：不动已经挂着的单子，可能只是一次抖动
- **超过10秒**：撤掉这个合约的全部挂单、暂停报价，此时订单簿两侧都是空的。**这是有意的取舍**：过期的报价留在订单簿里，谁比我们更早看到币安的价格，
  谁就能按旧价成交。想更倾向于"一直有报价"可以把这个时间调大，风险自己权衡
- 币安恢复后自动重新同步；进程退出（SIGTERM）时也会撤掉全部系统挂单
- 币安的行情接口在部分地区会返回451，部署前要确认能稳定访问

盘口过期时指数价也可能断：contract-api在指数价30秒没更新后冻结标记价、暂停强平，见 [mark-price.md](mark-price.md)。

## 配置

环境变量，不合法（不是正数）进程直接退出：

| 变量                     | 默认                   | 含义                                                                  |
|--------------------------|------------------------|-----------------------------------------------------------------------|
| `BOOKSYNC_API_URL`       | `http://127.0.0.1:7001` | contract-api地址（compose里是`http://api:7001`）                      |
| `BOOKSYNC_API_KEY_ID`    | 必填                   | API Key的id，**要同时有`trade`和`ops`权限**（建账户、下单撤单、给系统账户充值） |
| `BOOKSYNC_API_SECRET`    | 必填                   | 对应的secret                                                          |
| `BOOKSYNC_SYMBOLS`       | `BTCUSDT,ETHUSDT`      | 要同步的合约，必须是币安上也有的合约名                                |
| `BOOKSYNC_LEVELS`        | 50                     | 每侧同步币安盘口的前多少档，上限1000                                  |
| `BOOKSYNC_INTERVAL_MS`   | 1000                   | 每一轮的间隔                                                          |
| `BOOKSYNC_STALE_SEC`     | 10                     | 币安数据超过这么久没拉成功，就撤光挂单                                |
| `BOOKSYNC_UID_BASE`      | 9000000                | 系统账户的uid，占2个（买盘账户、卖盘账户）                            |
| `BOOKSYNC_BALANCE`       | 1000000000             | 系统账户的余额（USDT），低于一半时自动补到这个数                      |
| `BOOKSYNC_LEVERAGE`      | 5                      | 系统挂单的杠杆。全部保证金分档里最低的最大杠杆是5，用5在哪个档位都不会被拒 |
| `BOOKSYNC_KLINE_INTERVAL_SEC` | 2                  | K线每隔多少秒同步一次最近几根；设0=不同步K线（contract-api没设`external`时用，否则每次都被拒绝） |
| `BOOKSYNC_KLINE_BACKFILL` | 500                    | 启动时（和断了很久之后）每个周期最多补多少根历史，上限1500            |
| `BOOKSYNC_BINANCE_URL`   | `https://fapi.binance.com` | 币安合约行情地址                                                  |

## 部署

镜像有独立的`booksync`target，compose里的`booksync`服务在`booksync`这个profile下：**生产环境在`deploy/.env`里设`COMPOSE_PROFILES=booksync`**
（`deploy/.env.prod.example`已经设了）。先在`PERP_API_KEYS`里加一把 `booksync:<secret>:trade|ops`，再把同一个id和secret填到`BOOKSYNC_API_KEY_ID`、
`BOOKSYNC_API_SECRET`。进程不监听端口，靠日志和`restart: unless-stopped`。

测试环境默认不开：模拟客户端的做市（[sim-client.md](sim-client.md)）也会往订单簿里挂币安的盘口，**两者用同一段系统账户uid，不能同时跑**。

## 日志

| 日志                                                          | 含义                                                       |
|---------------------------------------------------------------|------------------------------------------------------------|
| `[WARN] 订单簿同步失败, symbol=...`                           | 这一轮失败（币安或我们的api出错），每个合约每30秒最多一条  |
| `[WARN] 同步币安指数价失败`                                   | 指数价没推成功，不影响挂单。服务端跳变保护拦下时也是这条   |
| `[ERROR] 币安数据已经超过10s没更新，已撤掉全部挂单、暂停报价` | 币安拉不到超过阈值。**要马上查**，此时订单簿是空的         |
| `[INFO] 币安数据恢复，重新同步订单簿`                         | 恢复了                                                     |

## 已知限制

- **不对冲，没有敞口限额**：系统是用户唯一的对手方，用户整体盈利时系统亏损，没有上限保护。系统账户的余额是配置的虚拟资金（默认10亿USDT），没有真实的资本约束
- **盘口比币安有延迟**：REST轮询每秒一次，加上等撤单生效，行情快的时候我们的最优价会落后币安。实测（一个波动很大的时段，2秒内币安价格变动近40美元）：
  我们的买一卖一相对币安平均落后约2.5美元（0.003%），最大约21美元（0.026%）。**谁比我们更早看到币安的价格，谁就有套利空间**，
  降低这个风险靠缩短间隔（`BOOKSYNC_INTERVAL_MS`）、以后改用WebSocket
- **用户的限价单可能改变我们的盘口**：订单簿引擎没变，用户挂在买卖价差里的限价单会成为新的买一/卖一，用户之间也可能互相成交。此时我们的盘口就不再完全等于币安
- **系统账户的仓位会累积**：多空各一份、不轧差，用余额兜着。用户结束本轮、被强平时的强制结算按标记价进行，没有对手方记账，系统的敞口在账上看不见
- **K线、24h统计的成交量是币安全市场的**，不是我们平台的；24h统计是最近24根1小时K线聚合，跟币安的滚动24h行情有约1%的差异
- **把币安的行情数据（盘口、K线）再分发给合作方是否合规，需要确认**：币安接口使用条款是否允许，我不确定，要你或法务核实
- **只有币安一家来源**：盘口、指数价和K线都来自币安，没有多来源交叉校验。指数价有服务端的跳变保护兜底（`PERP_INDEX_MAX_JUMP`，见 [mark-price.md](mark-price.md)）
- **数量精度跟着我们的合约配置走**：种子数据里ETHUSDT的`base_coin_scale`是2位、`volume_step`是0.01，币安更细的数量会被截掉，要跟币安一致需要调大这两个配置（`coins`表，见 [api.md](api.md)）

## 测试

`internal/booksync/`下的测试，币安用假的httptest服务，contract-api用假的内存后端（校验请求签名和`requestId`格式，检查挂单是否交叉、订单簿是否出现一侧为空）：

- **纯逻辑**：前N档原样、数量按合约精度取整、低于最小量不挂、差异计划（保留/撤/重挂/重复）、补挂的顺序规则
- **币安拉取**：响应解析、各种异常（451/429、空盘口、交叉、格式错误、价格为0）、指数价解析
- **K线**：币安K线解析和各种异常；六个周期各补历史、之后只同步最近几根、断了一阵后按错过的根数补、历史分批（200根一批）、
  api拒绝时不算已同步、一个周期失败不影响别的、每个合约各自同步、可以关闭。API侧（集成测试）：整根覆盖不是合并、只推变了的、
  非external时拒绝、整批校验（每种不合法的情况）、一批最大根数、最新价用币安K线收盘价（有我们自己的成交也不用）、24h统计来自币安1小时K线
- **同步循环**：第一轮建账户充值并原样挂出、余额够不重复充值、盘口没变不动、盘口变化跟随、被吃掉大半重挂；**行情上行/下行时同一轮补齐、任何时刻不出现一侧为空、
  不交叉**（撤单立刻生效、异步生效两种）、撤单一直不生效时不挂交叉的单；币安拿不到时10秒内不动/超过撤光/恢复后重挂；启动时币安一直拿不到也撤上个进程留下的单；
  一侧挂不出来不能只挂一侧；多合约互相独立；准备账户失败下一轮重试；退出时撤光；指数价每轮推送且和盘口互不牵连
- 变异检查：过期边界、不撤/不等、交叉规则、"先挂后撤"的每一步、档数、数量取整等全部被杀，只有只差日志的等价变异存活

另外用**真实的币安和整套系统**（api、engine、MySQL、Redis、Kafka）联调过：盘口价格与币安一致、指数价自动推进来、真实用户的市价单吃到系统的挂单、
大单的成交量和均价、停止进程后挂单撤光。这一步依赖外网，没有做成自动化测试。
