# 指数价喂价器（index-feeder）

生产环境的指数价喂价进程。定时从币安、OKX、Bybit三家的公开行情取各自算好的指数价，取中位数，校验之后调
contract-api的`POST /index-price`推进去。标记价靠指数价做锚，喂价断了强平会暂停，所以它是生产环境的必需组件，
见 [mark-price.md](mark-price.md)。代码在`internal/indexfeed/`（逻辑）和`cmd/index-feeder/`（进程入口）。

## 为什么要多来源

指数价是标记价的锚，标记价再决定强平。只接一家的话，这一家的接口被限流、返回错价、被地区封锁（币安部分地区返回451），
标记价就跟着断或跟着错。多来源取中位数：任何一家出问题都不影响结果，一家被操纵到离谱的价格也被中位数挡掉。

三家各自提供的已经是"指数价"（各家按多家现货交易所加权算出来的），不是合约的最新成交价，所以拿来当锚是合适的：

| 来源    | 接口                                                        | 取的字段                 |
|---------|-------------------------------------------------------------|--------------------------|
| binance | `GET /fapi/v1/premiumIndex?symbol=BTCUSDT`（fapi.binance.com） | `indexPrice`             |
| okx     | `GET /api/v5/market/index-tickers?instId=BTC-USDT`（www.okx.com）| `data[0].idxPx`          |
| bybit   | `GET /v5/market/tickers?category=linear&symbol=BTCUSDT`（api.bybit.com）| `result.list[0].indexPrice` |

都是不需要密钥的公开接口。OKX的instId由合约名转换（`BTCUSDT`→`BTC-USDT`），所以只支持`XXXUSDT`形式的合约名。
用REST轮询，默认每秒一轮，三家并行请求，单个来源超时2秒。

## 每一轮怎么算

每个合约独立处理：

1. **取价**：向所有来源并行取价，失败的来源丢掉（状态从成功变失败、从失败恢复时打一条日志，不刷屏）
2. **聚合**（`Aggregate`）：取中位数；偏离中位数超过`FEEDER_OUTLIER`（默认1%）的来源当离群丢掉；剩下的取中位数，
   数量不足`FEEDER_MIN_SOURCES`（默认2）家就 **不发布**。只有两家时中位数是均值，两家相差超过2%时各自离均值都超过
   1%、都被丢掉——两家对不上就不发布，不去猜哪家对
3. **跳变保护**：相对上次 **成功发布** 的价格变动超过`FEEDER_MAX_JUMP`（默认3%），先不发布，要连续
   `FEEDER_JUMP_CONFIRM`（默认3）个周期都落在同一个新价位（彼此偏差不超过离群阈值）才承认。真实的闪崩只是延迟
   几个周期（默认3秒）；单个来源的毛刺、抓取错位不会直接传到标记价上。中途价位又变了就从1重新计数。
   确认之后，只要发布还没成功，下个周期继续推同一个价位，不用重新数（服务端也有一道跳变保护，见下面）
4. **发布**：用API Key签名后调`POST /index-price`，签名用的是生产代码里的`api.SignRequest`。业务错误也是HTTP 200，
   发布方看响应体里的`code`，不是200就算失败；失败不更新"上次发布的价格"。
   一种失败要区分对待：`errCode=index_price_jump`是contract-api的**服务端跳变保护**在等这个新价位持续够久（默认
   3秒），不是故障——喂价器把它当WARN（不是ERROR），状态里记成"服务端跳变保护等待确认"，继续按周期推，服务端满了
   确认时间就承认。这样一次真实的大幅变动总共延迟约6到7秒（喂价器3个周期，加服务端3秒），见 [mark-price.md](mark-price.md)

任何一步拒绝发布，这个周期就不推，指数价会一直老下去，30秒后标记价冻结、强平暂停（见 [mark-price.md](mark-price.md)）。
这是有意的：喂价拿不准的时候，暂停强平比按错价强平安全。

## 配置

环境变量，不合法（不是正数）进程直接退出，不会悄悄退回默认值：

| 变量                   | 默认                | 含义                                                          |
|------------------------|---------------------|---------------------------------------------------------------|
| `FEEDER_API_URL`       | `http://127.0.0.1:7001` | contract-api地址（compose里是`http://api:7001`）          |
| `FEEDER_API_KEY_ID`    | 必填                | API Key的id，需要`ops`权限                                    |
| `FEEDER_API_SECRET`    | 必填                | 对应的secret                                                  |
| `FEEDER_SYMBOLS`       | `BTCUSDT,ETHUSDT`   | 要喂的合约，必须是三家都有的`XXXUSDT`                         |
| `FEEDER_SOURCES`       | `binance,okx,bybit` | 用哪些来源                                                    |
| `FEEDER_MIN_SOURCES`   | 2                   | 至少几家一致才发布，不能大于来源数（启动时检查）              |
| `FEEDER_OUTLIER`       | 0.01                | 偏离中位数超过这个比例算离群                                  |
| `FEEDER_MAX_JUMP`      | 0.03                | 单周期相对上次发布的变动超过这个比例要等确认                  |
| `FEEDER_JUMP_CONFIRM`  | 3                   | 跳变要连续几个周期确认                                        |
| `FEEDER_INTERVAL_MS`   | 1000                | 每一轮的间隔，必须明显小于30秒的断供阈值                      |
| `FEEDER_HEALTH_MAX_AGE_SEC` | 15             | 有合约超过这么多秒没成功发布，`/health`就返回503（要比30秒的断供阈值短，告警先响） |
| `FEEDER_HTTP_ADDR`     | `:7003`             | 状态和健康检查端口，设成`off`关掉。compose的健康检查固定探`127.0.0.1:7003`，用compose部署不要改它 |

## 部署

镜像有独立的`feeder`target（`make docker-build`会一起构建）。compose里的`feeder`服务放在`feeder`这个profile下，
**生产环境在`deploy/.env`里设`COMPOSE_PROFILES=feeder`** 就会跟着engine、api一起拉起（`deploy/.env.prod.example`
默认已经设了）。测试环境默认不开：模拟客户端的系统做市在喂指数价（还带行情情景偏移），两个喂价方会互相覆盖。

密钥：先在`PERP_API_KEYS`里加一把只有`ops`权限的密钥，格式`feeder:<secret>:ops`（逗号分隔），再把同一个id和secret填到
`FEEDER_API_KEY_ID`、`FEEDER_API_SECRET`。这把密钥不需要`trade`权限，也不要复用合作方的密钥。

进程只监听一个状态端口（7003，见下面"状态和健康检查"），compose里配了容器健康检查，`restart: unless-stopped`只在进程
退出时重启。要放到别的机器上跑也可以，只要能访问三家交易所和contract-api：

```bash
FEEDER_API_URL=http://api-host:7001 FEEDER_API_KEY_ID=feeder FEEDER_API_SECRET=... ./bin/index-feeder   # make build-feeder
```

## 状态和健康检查

进程在`FEEDER_HTTP_ADDR`（默认`:7003`）上有一个只读的HTTP服务。**不鉴权**：里面只有价格和来源的可用性，没有密钥，
也改变不了任何行为。compose里这个端口不映射到宿主机，需要从外面抓的话在compose里加端口映射或者让监控跑在同一个网络里。
端口起不来只会打一条ERROR，不影响喂价（喂价断了强平会暂停，比看不到状态严重得多）。

| 接口          | 返回                                                                                          |
|---------------|-----------------------------------------------------------------------------------------------|
| `GET /health` | 每个合约最近`FEEDER_HEALTH_MAX_AGE_SEC`（默认15秒）内都成功发布过返回200，否则503；两种情况body都是完整状态 |
| `GET /status` | 始终200，完整状态的JSON，给人看、给监控抓字段                                                  |

"健康"只看**有没有成功发布**，不看原因：来源不足、对不上、contract-api不可达、签名不对、被服务端跳变保护拦住太久，
最后都表现为"这个合约很久没发布成功"。还没发布过的合约从进程启动时间算起，刚启动的头15秒不算不健康。
阈值故意比30秒的断供阈值短：告警先响，强平暂停在后面，留出处理时间。

```json
{ "healthy": true, "startedAt": 1789776000000,
  "symbols": [ { "symbol": "BTCUSDT", "healthy": true, "lastPrice": "64800.5", "lastPublishAt": 1789776100000,
                 "publishAgeMs": 420, "lastSources": ["binance","bybit","okx"],
                 "issue": "", "issueAt": 0, "failStreak": 0 } ],
  "sources": [ { "source": "binance", "symbol": "BTCUSDT", "ok": true, "lastOkAt": 1789776100000, "lastError": "", "lastErrorAt": 0 } ] }
```

字段：`publishAgeMs`是距离上次成功发布多久（-1=还没发布过）；`issue`是最近一次没发布成功的原因，成功发布后清空，
`failStreak`是连续多少个周期没发布成功；`sources`是每个来源对每个合约的最近一次取价结果。`lastSources`比配置的来源少，
说明在降级运行。

**建议的告警**：
- `GET :7003/health`不是200（容器健康检查已经配好，容器会变`unhealthy`）。**注意`restart: unless-stopped`只在进程退出时重启，
  不会因为`unhealthy`重启**，所以这是给监控看的信号，不是自愈
- `/status`里任何合约`failStreak`持续增长，或者`lastSources`少于配置的来源数（降级运行，此时任何一家再出问题就会停发）
- 同一个来源的`ok`长时间是false

## 看日志

| 日志                                                   | 含义                                                                   |
|--------------------------------------------------------|------------------------------------------------------------------------|
| `[WARN] 指数价来源失败, source=... symbol=...`         | 某家取价失败（状态变化时才打），紧接着通常没有别的问题                 |
| `[INFO] 指数价来源恢复`                                | 那一家又好了                                                           |
| `[WARN] 指数价只用了2/3家来源`                         | 降级运行，每分钟最多一条。此时任何一家再出问题就会停发                 |
| `[ERROR] 指数价不发布, symbol=...`                     | 来源不足或对不上，每分钟最多一条。持续出现要马上查，30秒后强平会暂停   |
| `[WARN] 指数价相对上次发布跳变超过3%，等待确认(1/3)`   | 喂价器自己的跳变保护生效，确认后会打"大幅跳变已确认"（只打一次）       |
| `[WARN] 服务端跳变保护等待确认`                        | contract-api的跳变保护在等这个新价位持续够久，不是故障，几秒内会被承认 |
| `[ERROR] 发布指数价失败`                               | contract-api不可达、密钥没有`ops`权限、签名不对（时钟偏差超过窗口）等  |

## 已知限制

- **第一次发布没有跳变保护**：进程刚启动时没有"上次发布的价格"，第一个价格直接发布；重启也会清空。价格来源本身就是三家
  多来源取中位数，这一次的风险只是三家同时出错
- **三家交易所是同一个市场的镜像**：三家的指数价都由各自加权多家现货交易所算出，底层数据源有重叠。整个现货市场的价格
  异常时三家会一起偏，喂价器防不住这种情况；它防的是单家接口故障、单家指数计算出错、单点被限流封锁
- **状态输出是最小化的**：只有`/health`和`/status`两个JSON端点，没有Prometheus格式的指标（项目里没有这个依赖）。
  监控系统要么探`/health`，要么抓`/status`里的字段，见下面"状态和健康检查"
- **API侧的`POST /index-price`只有跳变保护、没有离群校验**：接口默认不校验；生产设`PERP_INDEX_MAX_JUMP=0.05`后，一次变动
  超过5%要新价位持续几秒才承认，但拿着ops密钥的人每次只挪一小步它挡不住。所以这把密钥要单独发、只给`ops`、妥善保管，
  见 [mark-price.md](mark-price.md)"服务端跳变保护"、[auth-design.md](auth-design.md)
- **只支持REST轮询**：每秒一轮，价格有秒级滞后，对标记价（本身有60秒基差窗口平均）没有影响

## 测试

`internal/indexfeed/`下的单元测试，没有外部依赖（交易所和contract-api都用`httptest`模拟）：

- **聚合**：手算的表驱动用例——三家一致、一家离群被丢、一家被操纵到2倍、两家一致、两家对不上拒绝、单家拒绝、偶数个来源取中间
  两个的均值、偏离恰好等于阈值不算离群、略超过算离群、要求3家但离群后只剩2家
- **来源解析**：三家真实接口的响应格式；HTTP非200、不是JSON、缺字段、价格为0或负数、OKX和Bybit的业务错误码（包括错误码
  非0但数据里带着价格的情况）、响应过大；OKX的instId转换
- **喂价循环**：三家取中位数、一家挂了照常发布、只剩一家不发布、两家对不上不发布、一家被操纵被忽略；跳变保护——超过3%要
  连续3个周期确认、恰好3%直接放行、一个周期的毛刺不会被承认、跳变期间价位又变了重新计数、发布失败不更新上次价格；
  合约之间互不影响
- **发布**：签名用生产的`api.SignRequest`重新算一遍，方法、路径、请求体都对得上；HTTP 200但业务错误、响应不是JSON都当失败；
  `errCode=index_price_jump`能用`errors.Is`认出是服务端跳变保护，别的业务错误不会被误认成它
- **确认后持续发布**：喂价器确认过跳变、服务端还在等确认时，每个周期都继续推，不用重新数3个周期；价位又变了要重新确认
- **状态和健康检查**（时钟可手动拨）：刚启动不算不健康、恰好15秒健康/超过就不健康、发布成功后恢复、来源不足/发布失败/服务端
  跳变保护各自的`issue`和`failStreak`、跳变等待确认的进度、来源的取价状态、一个合约不健康整体就不健康、阈值可配置、
  `/health`健康200/不健康503且body都带完整状态、`/status`始终200、只读（POST等方法405）

做过变异检查（去掉离群过滤、边界取开区间、去掉最少来源检查、跳变确认次数差一、发布前就更新上次价格、忽略业务错误码、
签错路径等18个），只有一个存活：`len(prices) < minSources`这个提前退出被改成`< 1`后行为等价，
后面对过滤之后剩余数量的检查已经兜住了，它只是让错误信息更清楚。

另外用真实的三家交易所和本地整套栈做过一次联调：喂价器连三家、签名推给contract-api，两个合约的指数价都在三家价格的范围内，
标记价跟着指数价走。这一步没有做成自动化测试，因为依赖外网和三家交易所的可用性。
