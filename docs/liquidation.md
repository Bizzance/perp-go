# 强平与保险基金

## 触发条件：全仓联合强平

`LiquidationService.RiskScanOnce`定时扫描全部有仓位的账户（`RiskScanIntervalMs`，默认2秒
一次），判断标准：

```
账户权益 <= 维持保证金要求
账户权益 = balance + credit + 全部持仓未实现盈亏
维持保证金要求 = (balance + credit) * (1 - lossRatio)
lossRatio = 未投保100%，已投保80%（LiquidationService.checkAndLiquidate，
            PositionService.LossRatioUninsured/LossRatioInsured）
```

`balance`是不随冻结/锁定变化的总额，本身已经包含了挂单/仓位占用的那部分钱，不需要再单独
加`frozenMargin`/仓位占用的保证金。早期实现只算自由余额（当时叫`available`），结果一开仓
权益就凭空少了整笔保证金——用户把钱全部用来开仓（充值653.25，开0.1 BTC的10倍多头，保证金
650+手续费3.25），价格一动不动，下一次风控扫描就把它强平了。买力（开仓够不够钱）用的是
另一个口径，只看自由余额`balance - frozenMargin`，见 [account-and-margin.md](account-and-margin.md)。

**未投保**：`lossRatio=100%`，维持保证金要求=0，等于"亏光全部余额(权益<=0)才强平"，全仓下
账户里的自由资金都是这个/这些仓位的缓冲，一直扛到穿仓为止，这是正常的风控流程。
**已投保**：`lossRatio=80%`，维持保证金要求=20%*(balance+credit)，亏损达到账户当前
balance+credit的80%就强平——投保保的是"整个账户当前的钱"，不是某一笔仓位单独的保证金，
这是产品口径上的简化决定（未来如果要支持"只投保一部分"需要重新设计）。用户随时可以投保，
`checkAndLiquidate`每次都读账户当前的投保状态，不是仓位开仓时锁定的快照，投保之后下一次
风控扫描立刻用新阈值判断。

**投保赔付**：账户一旦跌破投保阈值（`equity <= 维持保证金要求`且`IsInsured`），立刻按
`(balance+credit)*50%`发放信用额度赔付（复用`AccountService.GrantCredit`，`requestId`
按`uid+round`幂等，同一轮只发一次）——不等强平单真正成交，因为那时候balance已经被这次
亏损打没了，不是"投保基准"。赔付发放跟下面的强平/资金结算是两件独立的事：赔付看的是
触发那一刻的balance+credit，强平走正常的平仓流程，两者的时序、失败重试互不依赖。

一旦触发，这个uid名下 **所有**仓位（不分symbol）一起强平，不是只平触发条件的那一个仓位——
这是"全仓"模式的定义：风险共享，也共同承担强平。

`risk_limit_tiers`表（[risk-limit-tiers.md](risk-limit-tiers.md)）不再用于算维持保证金
要求，继续用于开仓/改杠杆的最大杠杆校验、以及下面强平单保护价的滑点缓冲。

**用的标记价不是最新成交价**：判断里的浮盈亏和维持保证金都按标记价算，标记价由指数价、盘口基差、最新成交价取
中位数得出，对敲拉高砸低成交价动不了它，见 [mark-price.md](mark-price.md)。指数价断供（超过30秒没更新）时，
持有这个合约仓位的账户 **不做强平判断，也不撤它的挂单**，喂价恢复后自动继续：宁可少强平，也不能按过期价格误强平。

## 强平触发时先撤掉全部挂单

风控扫描判定要强平后， **先撤掉这个uid的全部挂单和还没触发的条件单**（`EngineService.CancelAllPendingOrders`，
跨symbol、含条件平仓单），再挂强平单处理仓位。这是币安和OKX全仓强平的做法：

- 币安：全仓模式下触发强平时，"该交易者的所有挂单会被立即撤销"，不区分条件单、只减仓单
  （[Binance Futures Liquidation Protocols](https://www.binance.com/en/support/faq/binance-futures-liquidation-protocols-360033525271)）
- OKX：全仓下强平触发时先撤掉全部未成交订单（含机器人订单），再分步减仓；逐仓才只撤开仓方向、保留平仓的止盈止损
  （[OKX Forced liquidation FAQ](https://www.okx.com/en-us/help/forced-liquidation-faq)）

为什么要撤：挂单冻结的保证金退回账户，强平结算时才不会被漏算；账户风险已经触及强平线，也不该再让新的成交增加
仓位；也避免挂单跟自己的强平单撞上自成交保护。

几个取舍：

- **不撤单之后重新评估要不要强平**：OKX撤单后会重新评估，风险回到安全范围就不强平，因为它的保证金率把挂单
  占用算了进去。我们的权益（见上面）已经含挂单锁定的保证金，撤单只是解锁，权益不变，重新评估没有意义
- **强平单本身不撤**：强平单的成交结算是在`SubmitOrder`里先于"挂剩余量"执行的，这时把它标成已撤销，`SubmitOrder`
  接着还会把剩余量挂进订单簿，留下数据库已撤销、订单簿还挂着的幽灵单
- **分片部署下**只撤自己拥有的symbol的挂单（别的实例的订单簿摸不到），条件单只碰MySQL、不受限制
- **撤单失败**记ERROR日志、不中断强平：中断的话风险没法处理，比留几笔没撤掉的挂单更糟

## 强平后的资金结算（`HandleLiquidationSettleAftermath`）

每个仓位平完之后都会调用一次，但 **只有这个uid名下已经没有剩余仓位时才真正结算**：

- free balance是负的：先用free credit垫平（账户内部两个桶之间的挪用，不动保险基金）。
  垫不平剩下的缺口才是真穿仓：保险基金垫付，基金余额不够先用ADL补，balance清零
- free balance垫平/本来就非负：如果还有正数（维持保证金留下的缓冲），只把这部分balance
  扫进保险基金清零——**free credit一律不动**，不管是运营手动发的还是投保触发强平时自动
  赔付的，只要账户没结束本轮就留给用户继续交易，不会被这一步收回去

还有仓位没平完时什么都不做；全部平完后、读余额之前 **再撤一遍挂单**，作为兜底——强平窗口期里用户可能又挂了新单，
这些单锁定的保证金不在上面的自由余额+自由信用额度里，不撤的话自由余额为负时基金照常垫付，之后撤单把保证金解锁，
用户拿到的比真实权益多。全仓强平是同一个uid的各个仓位各自异步平仓，先平完的仓位结算后自由余额可能
暂时为负，但别的仓位的保证金还锁在`frozen_margin`里，平仓时会解锁，这时候垫付就成了多余的一进一出，还可能不必要地触发
ADL去强减无辜对手方的盈利仓位。同一个uid的这个结算用分布式锁串行，并且先确认没有剩余仓位、再读余额；不串行的话
两个仓位几乎同时平完会读到同一份缺口，各垫付一遍，账户反而多出一笔钱。

已知限制见 [known-limitations.md](known-limitations.md)：一次成交的结算不是原子的，所以多仓位并发强平时基金流水
可能有先垫付后回收的多余记录（总额守恒）。

## 分批强平：单批不超过`coin.MaxVolume`

`queueLiquidation`只负责原子标记`liquidating`+推送快照，真正的强平动作丢给独立goroutine
`liquidateInClips`异步循环处理——一个仓位可能要分好几批才能平完，不能占着风控扫描
（`RiskScanOnce`）这一次tick的时间。

每一批的挂单量不超过`coin.MaxVolume`——这是普通下单本来就有的单笔最大量限制
（`router.go`的`addOrder`同样校验），强平单没理由例外：一次性把一个远超正常单笔上限的
大仓位甩给盘口，对价格冲击太大，也超出这个symbol正常交易时的流动性预期。`MaxVolume`
配置为0（不限）时，行为退化成一批打完，等同于分批功能之前的样子，向后兼容。

依次处理每一批，两级机制在每一批内部各自独立运作：

1. **挂保护价限价单排队**（`submitLiquidationClip`）：按标记价格±维持保证金率×2倍缓冲
   算一个保护价，挂一张`reduce_only=true, liquidation=true`的限价单（数量按上面的批次
   截断），走正常撮合流程排队成交。保护价缓冲的思路借鉴真实交易所"破产价附近留保护价"——
   不是按最优价格甩卖，给一点滑点空间换成交确定性。标记价格/分档配置在 **每一批**都重新
   查一次，不是整个强平流程开始时查一次就复用到底——大仓位分批下来跨越的时间可能不短，
   中途行情可能已经移动，用陈旧的价格算保护价没有意义。
2. **超时兜底直接结算**（`settleTimeoutFallback`）：这一批挂出去`LiquidationOrderTimeoutMs`
   （默认10秒）还没成交完，撤掉这一批剩余的部分，按当前标记价直接结算，不再等真实撮合——
   注意是"这一批"没成交的量，不是整个仓位剩余的量，两者在分批强平下不再相等。终态按
   `min(仓位剩余量, 委托剩余量)`是否覆盖了委托的全部剩余量分别写`filled`/`canceled`——
   完全覆盖才是`filled`；如果这期间仓位量被别的路径也动过、导致实际吃到的比委托剩余量
   更少，标`canceled`（等同于"部分成交之后剩余部分被撤销"），不能标`filled`，否则
   `RecoverOrderBook`未来进程重启时会漏查这笔委托（只查`open`/`partially_filled`），
   跟MARKET单缺对手盘那个终态判断是同一套逻辑，见 [known-limitations.md](known-limitations.md)。

`SubmitOrder`是同步撮合的，一批挂单提交之后如果立刻就被吃满/取消（大部分正常流动性下
应该如此），不需要傻等满`LiquidationOrderTimeoutMs`才检查，马上进入下一批；只有真的没
成交完才等超时兜底。全部批次处理完（仓位volume归零）循环正常退出；中途任何一步没法继续
（缺标记价格/缺分档配置/查`coin.MaxVolume`配置失败/落库失败）会把状态撤回`normal`，
交给下一轮风控扫描重新判断——不重试同一批，这些失败原因不是"运气不好"，立刻重试大概率
还是失败。查`coin.MaxVolume`配置这一步专门做成失败关闭（DB查询出错或查到`nil`都当失败
处理，不能悄悄用未截断的`p.Volume`当这一批的量往下走）——DB不稳定的时候恰好是最不该
放松"单批不超过`MaxVolume`"这道安全阀的时候，已用真实压测验证过：连续查询失败期间
每一轮风控扫描都正确中止并留给下一轮重试，不卡死也不绕过限制，见
[known-limitations.md](known-limitations.md)。

`positions.status`在整个强平流程（从第一批到最后一批）期间都是`liquidating`，
`MarkLiquidating`是一次原子guard，保证同一个仓位不会被同一轮/连续几轮扫描重复挂出强平
流程——这个guard能生效的前提是`liquidating`标记在整个分批流程期间不会被中途清掉。
早期`ApplyCloseFill`（每一批clip自己的成交结算也走这个函数）无条件把`status`写回
`normal`，等于每处理完一批就把这个标记自己擦掉，让`MarkLiquidating`的guard重新被满足、
下一轮风控扫描把同一个仓位第二次标记`liquidating`、派生出第二个并发的`liquidateInClips`
协程——已经用真实压测复现过（构造价格驱动亏损始终跑赢单批保证金释放的场景），修复成
`ApplyCloseFill`只在仓位数量真正归零时才把状态改成`closed`，其余情况原样保留调用前的
状态，重新验证过同一仓位只会成功`MarkLiquidating`一次。详见
[known-limitations.md](known-limitations.md)。

## 强平结算后的两个分支（`HandleLiquidationSettleAftermath`）

结算完之后看账户自由余额+自由信用额度合计：

1. **穿仓（合计`< 0`）**：保险基金垫付缺口。基金余额不够覆盖这次缺口时，先触发ADL
   （见下面"自动减仓"一节）强制减仓对手方最赚钱的仓位补一部分，补不满的部分仍然由基金
   硬扛（基金余额允许变负，代表系统亏空，MVP阶段只记日志告警，不做熔断）。
2. **有维持保证金缓冲（合计`> 0`，且这个uid已经没有剩余仓位）**：这部分是维持保证金
   要求留下的缓冲， **不退给用户**——真实交易所是按破产价结算、多出来的差价当清算费进保险
   基金；这里不改结算价格/撮合逻辑，改成结算完直接把这部分正数余额扫进保险基金、账户清零，
   经济结果等价。

缓冲清算的扣款方向跟日常亏损（手续费、已实现盈亏）保持一致：都是先动`balance`，不单独
为强平缓冲设计不同的清算顺序。

## 自动减仓（ADL）：保险基金不够时，强制减仓对手方最赚钱的仓位

`runADL`（`internal/service/adl.go`）不是让被强平仓位跟ADL目标在盘口上真的撮合成交一笔
（那样需要在撮合链路里插入一种新的委托来源，复杂得多），而是两次独立的强制结算分别完成：
被强平方已经在`HandleLiquidationSettleAftermath`的上一步按标记价结算过了，这里对ADL目标
也按标记价强制平掉需要的量、正常结算它自己的已实现盈亏，然后单独从这笔刚到账的盈利里划
一部分给保险基金。两次结算加起来的经济结果，跟"两者直接在盘口按标记价成交一笔"是等价的
（都是：被强平方在标记价了结、对手方也在标记价了结、差额去处一致），只是实现上不用改
撮合链路。

**目标方向**：跟被强平的仓位方向相反——多头被强平是因为价格下跌亏钱，这次下跌真正让谁
赚钱只可能是空头，ADL找的是空头里最赚钱的仓位，不是随便挑一个方向。

**排序**：候选仓位（这个symbol上方向相反、`status=normal`、未实现盈亏`>0`的仓位）按ROE
（`未实现盈亏/PositionMargin`）降序——同样的名义盈利，杠杆越高/占用保证金越少，ROE越高，
越优先被选中，思路跟真实交易所ADL队列排序一致。亏钱的仓位不会被选中，减了也筹不到钱。

**减仓量**：按需要筹到的金额反推，不是整个仓位一把梭——`需要筹的金额 / 这个仓位当前
每单位的盈利`算出这一个候选需要平掉多少量，如果这个候选全部平掉都不够，全平之后移到
下一个候选继续凑，直到筹够或者候选池耗尽。筹不够的部分仍然由保险基金自己硬扛，这是
明确接受的取舍：极端单边行情下，亏钱的一方和赚钱的一方本来就可能严重不对称，基金兜底
始终是最后一道防线。

## 保险基金

`insurance_fund`表全局唯一一行，`insurance_fund_ledger`记流水。`InsuranceFundService.Adjust`
的`amount`正数=强平盈余注入/ADL划转注入，负数=基金垫付穿仓亏损，无熔断机制——余额变负只打
`[WARN]`日志。

详见 [known-limitations.md](known-limitations.md)。

## 实测验证

**分批强平**：用真实的多批场景验证过：把`coin.MaxVolume`临时调成一个远小于持仓量的值
（比如持仓0.03、单批上限0.01），触发强平后engine日志依次打出3批"触发强平-挂单排队"
（本批量=0.01，仓位剩余量分别是0.03/0.02/0.01），中间没有真实对手盘时每一批各自等满
超时、兜底结算，最终仓位归零、维持保证金缓冲只在最后一批处理完之后扫入保险基金一次
（不是每批都扫一次）、委托历史里能看到3笔独立的`filled`委托、每笔`Amount`都精确等于
批次上限，不是一笔`Amount=0.03`的大单。

**ADL**：用真实的穿仓场景验证过：保险基金余额先清零，构造一个高杠杆多头仓位和一个
方向相反的空头仓位，直接操作标记价格制造一次大幅下跌（多头深度浮亏、空头深度浮盈），
触发强平后多头账户穿仓，ADL正确按ROE降序选中空头候选（测试环境里凑巧有两个候选，日志
显示先减了ROE更高的那个、剩余需求不够再减第二个），减仓量精确对应"筹够需要的金额"而
不是整个仓位、被ADL的仓位保证金/可用余额按精确比例结算、保险基金最终余额精确等于
"ADL筹到的金额-穿仓缺口"（本例中两者相等，基金停回0，不是继续变负）——全链路的数字
一步步手算核对过，跟实际结果完全吻合。
