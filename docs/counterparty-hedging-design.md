# 生产环境的对手方与对冲（方案草案）

> **状态：方案草案，没有对应代码，等待决策。** 这份文档回答"上线之后用户的对手方是谁、系统持仓怎么对冲、亏损谁来承担"，
> 第8节列出了需要产品/运营拍板的问题，每个问题都带了建议。决策之前不写代码，其它文档记录的是当前代码的实际行为，这一份不是。
>
> **已确定（产品方的回答）**：没有第三方做市商；流动性来自引入币安的行情和订单簿，用户的对手方就是我们系统。
> 所以方案A（外部做市商）已排除，流动性模型是"镜像币安订单簿"。还没定的是：系统持有的敞口自己扛还是去币安对冲（B/C/D），以及亏损谁来承担。

## 1. 要解决什么问题

产品设定是上线后用户的对手方就是系统（合作方的用户在我们这里交易，我们是他们的对手）。但生产环境现在：

- **没有任何做市方。** `tools/sim-client`的系统做市只是测试工具，不进生产镜像，见 [sim-client.md](sim-client.md)。订单簿是空的，用户下限价单没人成交，
  市价单直接撤销
- **系统的头寸和盈亏在账上看不见。** 下面第2节会说明，系统其实已经是一部分成交的对手方，只是没有记账
- **没有对冲。** 系统做了对手方以后，用户赢多少系统就亏多少，没有任何东西去抵消这个敞口

这三件事必须先设计清楚再上线，因为它们决定生产环境**能不能跑起来，以及最坏会亏多少**。

## 2. 现状盘点（都从代码里核实过）

### 2.1 撮合层是纯订单簿

`internal/matching`是价格-时间优先的订单簿，成交发生在两笔真实委托之间（[matching-and-settlement.md](matching-and-settlement.md)）。没有"系统自己当对手方"的概念，
系统账户和普通账户在代码里没有任何区别：没有账户类型字段，没有强平豁免，没有敞口限制。

### 2.2 有三条路径不经过订单簿，只结算用户这一侧

| 路径                               | 代码                                                | 结算价   | 对手方   | 记账                              |
|------------------------------------|-----------------------------------------------------|----------|----------|-----------------------------------|
| **结束本轮**（`POST /account/round/close`）| `EngineService.CloseRound`→`forceCloseOnePosition`   | 标记价   | 没有     | 只有用户的已实现盈亏              |
| 强平的超时兜底                     | `LiquidationService.settleTimeoutFallback`          | 标记价   | 没有     | 只有用户的已实现盈亏              |
| ADL对手方强减                      | `EngineService.runADL`→`forceCloseOnePosition`       | 标记价   | 没有     | 被减仓用户的盈利，一部分划给保险基金 |

这三条路径都**不经过撮合**，直接调`SettlementService.SettleFill`按标记价结算：结束本轮和ADL新落一笔"已成交"的市价委托，强平兜底是把已有的强平委托按标记价直接成交。
`trades`表只在正常撮合成交时写（`EngineService.settleOneFill`），所以这三条路径**没有成交记录，没有对手方，没有系统账户的分录**。
后果：用户在这些路径上的盈利是凭空产生的，亏损也是凭空消失的，全系统"所有账户已实现盈亏之和 + 手续费 = 0"这个恒等式在这些路径上不成立。

其中**结束本轮不是边角路径，而是产品的正常流程**：交易以轮为单位，客户端告诉我们本轮结束，我们就按标记价平掉全部仓位（[account-and-margin.md](account-and-margin.md)"轮次"一节）。
也就是说，每一轮结束时，系统已经是所有仓位的隐式对手方——只是账上看不见，风险也没人管。**"用户的对手方就是系统"在代码里其实已经发生了，缺的是记账、敞口管理和对冲。**

### 2.3 已有的兜底

- **保险基金**（[liquidation.md](liquidation.md)）：只吸收用户强平后的穿仓缺口，不是做市亏损的资金池。余额允许变负，只打WARN日志，没有熔断
- **ADL**：保险基金不够时强减盈利的对手方仓位。目前选的是"方向相反、最赚钱的仓位"，不区分用户和系统账户（系统账户以后如果是盈利的对手方，就会被选中）
- **信用额度**：用户买保险后运营发放的赔付，只能当保证金，不能转出。亏损先扣`available`再扣`credit`，盈利只进`available`（[account-and-margin.md](account-and-margin.md)）

### 2.4 模拟客户端的做市不能直接搬到生产

它把币安盘口按价格桶镜像成我们订单簿里的挂单，账户就是普通账户，用10亿USDT的余额兜着，仓位随用户交易累积、多空不轧差，
累积多了靠人工点"重置系统账户"（结束本轮）清掉。没有对冲、没有敞口限额、没有止损，也没有资金约束——这些对测试无所谓，对生产都是致命的。

## 3. 三个必须回答的问题

1. **对手方是谁？** 谁在订单簿里挂单，用户的单子跟谁成交
2. **敞口怎么处理？** 对手方成交后持有的净头寸，是自己扛、还是去外部交易所对冲掉
3. **亏损谁来承担？** 做市亏损、对冲失败的亏损、信用额度赔付的成本，各自由哪一层出钱

## 4. 方案选项

| 方案 | 做法                                                                                                   | 系统承担的风险                                       | 主要代价                                                     |
|------|--------------------------------------------------------------------------------------------------------|------------------------------------------------------|--------------------------------------------------------------|
| ~~A~~ | ~~**外部做市商**：系统不持仓，引入第三方做市商账户在订单簿挂单~~ **（已排除：没有做市商，对手方就是系统）** | -                                                    | -                                                            |
| B    | **系统做市，不对冲**：系统账户挂单、自己持有全部敞口                                                   | 最大：用户整体盈利=系统亏损，行情单边时亏损无上限    | 需要大额资本金；等于系统在跟用户对赌                         |
| C    | **系统做市，全额对冲**：每笔成交后立刻在外部交易所（币安等）反向开仓，敞口接近0                        | 对冲延迟窗口、对冲失败、外部交易所风险、资金费率差   | 对冲手续费和滑点；外部交易所保证金占用；对冲引擎复杂         |
| D    | **系统做市，只对冲净敞口**：系统账户的多空先内部轧差，净敞口超过阈值才去外部对冲，同时有敞口限额和熔断 | 阈值以内的敞口自己扛；其余同C                        | 比C省手续费，但要有敞口限额、阈值参数和熔断                  |

现在剩下B、C、D三个（都是系统做对手方，区别只在敞口怎么处理）。**建议：D，分阶段落地**（第7节）。理由：

- 用户在同一个合约上的多空天然会互相抵消，先轧差再对冲比逐笔对冲省手续费和外部保证金
- 第一阶段只做"可见、可控"（显式系统账户、敞口监控、限额、熔断），**不接外部交易所也能把最大亏损限定在一个预先设好的资本金预算里**，
  对冲引擎是最大的工程和风险，放到后面、先用影子模式验证
- 流动性模型是镜像币安订单簿，这天然适合在币安对冲：用户吃掉我们的某一档，币安上同一价位附近就有对应深度，
  只要吃掉的量不超过镜像出来的量，对冲滑点就小

## 5. 推荐方案的组成

```
   用户/合作方  ──▶  contract-api ──Kafka──▶ contract-engine ◀── market-maker(新)   系统账户按币安订单簿在我们订单簿里挂单
                                                   │
                                          成交、强制结算都记到系统账户
                                                   │
                     exposure API(新, ops) ◀───────┘
                            │
                        hedger(新) ──▶ 外部交易所(币安等)   对冲净敞口；限额和熔断先于对冲生效
```

### 5.1 系统账户显式化

- `accounts`增加账户类型（`user` / `house`），系统账户是一等公民，不再是"碰巧余额很多的普通账户"
- 系统账户的规则要**单独定义**，不能默认继承普通账户的规则：
  - **强平**：系统账户不参与强平（强平自己的做市账户只会让风险失控），风险由敞口限额和资本金监控管
  - **ADL**：是否可以被ADL选中需要决策（第8节Q6）。被强减会让对冲敞口变化，hedger按持仓重新计算所以会自愈，但要能看见
  - **信用额度、冻结、投保**：不适用
- 系统账户的资金、头寸、盈亏有独立的报表，和用户、保险基金分开

### 5.2 让三条隐式路径变成显式的

结束本轮、强平超时兜底、ADL这三条路径，每笔强制结算都要**同时记一笔系统账户的对手分录**（对手方仓位、已实现盈亏），
这样"全系统已实现盈亏之和 + 手续费 = 0"重新成立，系统的敞口也真实地反映在系统账户的持仓里，能被监控、被限额、被对冲。

这是第一阶段最重要、也最容易被忽略的工作：**不做这一步，即使有了做市和对冲，每一轮结束时用户的盈亏依然凭空进出。**
需要决策的是强制路径的对手方是哪个系统账户、多个系统账户时怎么分（第8节Q6）。

### 5.3 敞口与限额

- **敞口**：每个合约的系统净头寸 = 全部系统账户的多头量 − 空头量（基础币数量，再乘标记价得到名义价值）
- **对外查询**：新增ops权限的接口返回每个合约的净敞口、系统账户权益、已实现和未实现盈亏，供做市、对冲和监控使用
- **限额**（数值由你定，第8节Q3）：单合约最大净敞口名义价值、全部合约合计的最大敞口、系统账户最大回撤
- **限额动作是分级的**：接近限额时做市方收窄报价规模/加大倾斜；达到限额时**停止在增加敞口的方向上挂单**；触发熔断条件时撤掉全部系统挂单、停止做市（不平仓，等人工）
- **熔断条件**（建议）：指数价断供、对冲不健康（第5.5节）、系统账户回撤超限、敞口超过限额且对冲追不上、外部交易所不可达超过一定时间

### 5.4 做市（market-maker进程，生产版）

流动性模型已经确定：**镜像币安的订单簿**。这正是`tools/sim-client/maker.go`的做法（按价格桶聚合、撤/补的差异计划、先撤后挂避免自成交、
出错不动已有挂单），生产版在它的基础上要补上测试工具不需要的东西：

- **保护性价差**：不能把币安的买卖价原样镜像。我们的报价有延迟（REST轮询有一个周期的滞后，见 [sim-client.md](sim-client.md)"限制"），加上对冲成本，
  价差要能覆盖这两项，否则每笔成交平均都在亏。价差大小是产品参数，等Q3的风险预算一起定
- **报价滞后要能检测**：币安行情的最后更新时间超过阈值，或者币安价格在一个周期内跳变超过阈值，就撤掉全部报价，不能拿过期的价格挂单等着被吃
- **每一档的规模有上限**：镜像币安某一档的真实数量会把外部盘口的深度变成我们的敞口，每一档数量、总挂单量都要乘缩放系数并受限额约束，
  不能让一次成交后的敞口越过限额
- **库存倾斜**：净敞口偏多就下调买盘规模/买价，反之亦然，让敞口自己回中
- **停止条件**同5.3的熔断，另外任何一步失败都不能留下过期报价
- 用系统账户的`trade`权限密钥，不需要`ops`；独立进程，参照index-feeder的部署方式（独立镜像、compose profile、健康检查端口）；
  行情源不能只有币安一家的一个接口（喂价器已经有三家来源取中位数的做法，做市的行情源要做同样的容错）

### 5.5 对冲（hedger进程）

流程（每秒一轮，跟喂价器同样的节奏）：

1. 通过exposure API读每个合约的系统净敞口`N`（基础币数量）
2. 读外部交易所上对冲账户的当前持仓`H`（**先读交易所，不信本地记忆**，重启后靠它恢复）
3. 目标是`H = −N`。只有`|N + H|`超过**对冲带宽**才下单（省手续费、避免来回抖动），下单量是把差补到目标
4. 用限价IOC（限定最大滑点）而不是无脑市价，`clientOrderId`由（合约, 序号）确定性生成，重试不会重复下单
5. 下单后再读一次持仓确认，把对冲结果、滑点、手续费记下来供对账

故障处理（都要有明确行为，不能靠运气）：

| 情况                          | 行为                                                                              |
|-------------------------------|-----------------------------------------------------------------------------------|
| 交易所不可达/被限流/地区封锁  | 重试并告警；对冲不健康标志置位 → 做市停止扩大敞口。币安部分地区会返回451，见 [index-feeder.md](index-feeder.md) |
| 下单被拒（保证金不足等）      | 告警，不健康标志置位；**不能静默丢弃这次对冲**                                    |
| 对冲仓位被外部交易所强平      | 下一轮读到持仓变化后重新对冲，同时告警；外部账户保证金率要单独监控和告警          |
| hedger进程崩溃                | 敞口不再被对冲，健康状态过期 → 做市按限额收缩。重启后先读交易所持仓再继续         |
| 系统持仓和对冲持仓长期对不上  | 对账告警，超过阈值触发熔断                                                        |

`hedger`自己没有数据库，只通过ops权限的HTTP接口读敞口、通过交易所API下单。交易所API密钥只开交易权限、**不开提现**、绑定IP白名单。
有"影子模式"：只计算并记录"本来会下的单"和当时的盘口价，不真下单，用来在上线前对账验证。

### 5.6 亏损瀑布

建议按下面的顺序承担，**各层资金分开记账、不混用**：

1. **系统做市账户的资本金**：做市亏损、对冲滑点和手续费先从这里出。这一层耗尽前必须触发熔断，不允许"亏光了继续做市"
2. **熔断**：不是钱，是动作。达到限额后不再增加敞口
3. **保险基金**：**只用于用户强平后的穿仓缺口**（现有语义），不用于做市亏损。混用会让穿仓和做市两个风险互相污染，谁也算不清
4. **运营/合作方兜底**：资本金不够时谁补，需要合同层面确定（第8节Q4）
5. **ADL**：保持现状，作为极端行情下最后一道线

信用额度的成本单独看（第6节）。

## 6. 风险清单

| 风险                             | 说明                                                                                                                                             | 缓解                                                             |
|----------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------|
| **对冲延迟窗口**                 | 用户成交到对冲完成之间敞口是裸露的，单边行情下窗口内的价格变动就是亏损                                                                           | 对冲带宽和限额、限价IOC的滑点上限、窗口内敞口按限额封顶          |
| **报价滞后（逆向选择）**         | 镜像币安订单簿，币安价格一动、我们的报价还没跟上时，用户可以吃掉过期的报价，再等我们去币安对冲时已经是更差的价格。这是镜像模式固有的风险，价格波动越快越明显 | 保护性价差、行情最后更新时间和跳变检测后撤掉报价、每一档规模上限（5.4） |
| **资金费率差**                   | 用户这一侧收付的是我们的资金费率（冲击价格溢价的TWAP，见 [funding-rate.md](funding-rate.md)），对冲那一侧收付的是外部交易所的资金费率，两者不一样，系统账户就有差额 | 对账里单列"资金费率差"；必要时后续让费率口径向外部对齐          |
| **信用额度是不对称的敞口**       | 信用额度当保证金，盈利进`available`（可转出），亏损先扣`available`再扣`credit`。如果发放时账户`available`已经所剩无几，用户是拿一份不用自己出钱的保证金交易：赢了归自己，输了最多输掉赔付。对手方（系统）承担的是不对称的风险 | 保险定价要覆盖它；对信用额度开出的仓位单独限制杠杆或名义价值（Q5） |
| **外部交易所风险**               | 故障、限流、地区封锁、对冲账户被强平、账户被风控冻结                                                                                             | 5.5的故障处理；对冲账户保证金监控；必要时准备第二家交易所        |
| **资金在两处**                   | 对冲账户的保证金在外部交易所，资金划转（我们↔交易所）需要托管和审批流程                                                                          | 资金划转走人工审批，监控外部账户余额，设置最低余额告警           |
| **标记价/指数价失真**            | 系统的盈亏、限额、对冲都依赖它们                                                                                                                 | 已有：多来源中位数、跳变保护、断供冻结，见 [mark-price.md](mark-price.md) |
| **合规与地区**                   | 系统做对手方、在境外交易所对冲、资金跨境，可能有牌照和地区限制                                                                                   | 需要你确认（Q7），不在本文档范围                                 |
| **测试环境和生产混淆**           | sim-client的做市账户和生产系统账户不能混                                                                                                         | 账户类型区分；sim-client继续只用于测试环境                       |

## 7. 分阶段落地与上线门槛

| 阶段 | 内容                                                                                                                  | 进入下一阶段的门槛                                                                                   |
|------|-----------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| P0   | 本文档：做决策（第8节）                                                                                               | 第8节的问题有答案，尤其是Q1、Q3、Q4                                                                  |
| P1   | **可见可控**：账户类型、三条隐式路径补对手分录、exposure API、限额和熔断、系统账户报表和对账                          | 集成测试证明恒等式（全系统已实现盈亏+手续费=0）在三条强制路径上成立；限额和熔断有测试并做过变异检查  |
| P2   | **生产做市**：market-maker进程，只在限额内报价，先不对冲，资本金设小                                                  | 模拟盘/小额压测里敞口始终不越限、熔断触发后确实撤单；最大亏损被资本金封顶                            |
| P3   | **对冲**：hedger先影子模式，再真下小额单；对账（系统持仓 vs 对冲持仓、滑点、手续费、资金费率差）                       | 影子模式对账一段时间无异常；故障注入（交易所不可达、下单被拒、进程重启）行为符合5.5                  |
| P4   | 放量：加大资本金和限额，增加合约，考虑第二家对冲交易所                                                                | 按业务需要                                                                                           |

**P1本身就是上线门槛**：没有系统账户的记账和敞口限额，就不应该让真实用户进来，因为每一轮结束系统都在无记录地承担风险。
